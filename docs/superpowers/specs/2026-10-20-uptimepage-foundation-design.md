# UptimePage 重写：需求与基础架构

日期：2026-10-20。

本文记录用户逐项确认的需求和基础架构，作为后续 UI/UX 设计及实现的约束。本文不是完整的页面规格或实施计划，不代表已实现或已在 EdgeOne 上验证。

## 1. 目标与边界

- 完全重新设计和重写，不沿用旧项目的技术实现。UptimeRobot 鉴权和请求方式可以参考旧实现，也可以直接依据官方文档。
- 本站只负责获取、整理、缓存和展示监控数据。检查任务与告警由上游负责。
- 首发支持 Peekaping 和 UptimeRobot。对话中的「peekingapi」均指 Peekaping。
- 只支持 EdgeOne Makers 部署，保留本地开发和预览能力，不适配 Docker。
- 所有页面公开，不做访客账号、登录或访问密码。
- 不建设长期历史数据库，不补造缺失数据。
- 第一版通过配置文件管理，可视化配置编辑器属于后续工作。
- 当前使用规模约为两个来源各 50 个监控。配置不设置来源、分组或监控的固定数量上限，实际容量仍受平台与上游配额限制。

## 2. 分组与公开范围

每个大分组独立绑定一个数据源连接，不在大分组之间混合监控。相同类型的数据源可以配置多次。

```text
大分组：ID、显示名称、Logo、来源类型、连接配置
  ├─ 子分组：ID、显示名称、Logo、监控选择规则
  └─ 子分组：ID、显示名称、Logo、监控选择规则
```

- Peekaping：每个大分组配置一个服务端 API Key 引用，子分组通过状态页别名获取允许公开的监控 ID，再按需补取详细数据。
- UptimeRobot：每个大分组配置一个服务端 API Key 引用，子分组通过监控 ID 列表选择监控。
- 未被任何子分组选中的监控不能通过本站查询或展示。
- 同一个监控允许加入同一大分组下的多个子分组。
- 「全部」是自动生成的子分组入口，只合并当前大分组的监控，按上游监控 ID 去重，不按子分组分段。
- 同一大分组内，监控的名称覆盖等展示设置按监控 ID 统一维护。子分组负责选择和排序。
- 不同大分组中的同名或同 ID 监控不视为同一个本站条目。本站标识由大分组 ID 与上游监控 ID 共同确定。

## 3. 页面结构与访问

- 首页包含顶部导航、大分组切换、子分组切换、监控列表和页脚。
- 默认选择配置中的第一个大分组及其「全部」入口。
- 大分组和子分组都在首页切换，不为分组单独设计内容页。
- 列表条目采用瘦长卡片，点击进入该监控的独立详情页。
- 详情链接使用大分组 ID 与上游监控 ID，不依赖显示名称或子分组 ID。
- 改名或调整子分组归属不改变详情链接；移出公开范围后，详情查询停止返回该监控的数据。
- 大分组、子分组默认按配置顺序排列。
- 监控默认沿用上游顺序，允许配置手动顺序；「全部」按子分组顺序合并，重复项保留首次出现的位置。
- 默认不自动置顶异常条目，但允许配置开启；同类条目保持原有顺序。

卡片字段、详情页组成、图表、视觉风格、响应式布局，以及哪些状态参与异常置顶，属于后续 UI/UX 与状态映射设计范围。此前讨论过的字段建议不作为本阶段已确认要求。

## 4. 国际化与访客偏好

- 支持国际化，首发提供简体中文和英文。
- 自动匹配浏览器偏好语言，无法获取或匹配时回退英文。
- 网站介绍、分组名称、页脚等自定义内容允许配置中英文，也允许只填写通用文本。
- 监控名称默认来自上游，可按监控 ID 配置通用文本或中英文名称，不修改上游数据。
- 导航栏提供偏好设置按钮及弹出菜单，用于语言、时区和深浅色设置。菜单的具体组织留给 UI/UX 设计。
- 时区默认跟随浏览器，获取失败时回退 UTC。
- 深浅色默认跟随系统。
- 手动设置优先于自动设置，保存到当前浏览器；允许恢复自动模式。
- 接口统一使用 UTC 时间，页面按所选时区显示，时间轴注明时区。

## 5. 技术方案

采用 React、Vite、TypeScript、Tailwind CSS 与 EdgeOne Cloud Functions；Edge Functions 提供节点缓存和可选 KV 桥。交互组件采用成熟的无障碍组件方案，具体库与版本在后续设计和实施计划中选择。

```text
静态页面与资源
      ↓
本站只读接口
      ├─ 配置与公开名单检查
      ├─ 节点缓存 / 可选 KV 快照
      └─ 来源适配 → Peekaping / UptimeRobot
```

职责划分：

| 部分     | 职责                                                 |
| -------- | ---------------------------------------------------- |
| 前端     | 分组切换、详情路由、偏好设置、数据展示与更新         |
| 配置处理 | 构建时校验，将公开内容与服务端连接配置分开输出       |
| 本站接口 | 参数限制、公开范围检查、按需取数、缓存、筛选公开字段 |
| 来源适配 | 各自处理上游鉴权、分页、限流、状态映射和数据能力差异 |
| 缓存适配 | 封装节点缓存和可选 KV，避免页面依赖平台存储细节      |

前端使用统一的数据结构，不直接依赖上游响应格式。数据接口不承担监控调度、管理或告警职责。

## 6. 配置的用途与处理时机

使用 JSON 配置。网站设置与监控配置可以放在同一份文件中，但处理时机和产物必须区分。

### 6.1 网站设置

标题、Logo、导航、页脚、多语言文本及相关行为设置在构建时处理，产出静态页面、资源和公开配置。部署后不通过数据接口读取网站设置。

### 6.2 监控配置

- 分组 ID、显示名称、Logo 等公开信息在构建时提供给前端。
- 来源连接地址、密钥环境变量名、监控选择规则及服务端展示设置由服务端函数使用；不将完整服务端配置打包进浏览器资源。
- 实际监控数据运行时获取。
- 修改配置文件后需要重新部署。
- 密钥实际值只保存于服务端环境变量中，JSON 只保存变量名引用。

### 6.3 构建校验

- 校验必填项、来源类型、ID 唯一性、引用关系和选择规则，错误应指出配置位置。
- 大分组 ID 在站点内唯一；子分组 ID 在所属大分组内唯一。
- 同一监控出现在多个子分组是合法配置，不按重复错误处理。
- 上游暂时不可达属于运行时故障，不以联网成功作为构建前提。
- 配置编辑器后续可导入、编辑、校验、预览并导出配置，第一版不实现。

## 7. 取数与数据口径

### 7.1 按需加载

- 首页只获取当前大分组的数据，不提前请求所有大分组。
- 详情页打开后才获取该监控的历史、统计和证书等详细数据。
- 处理上游分页，不能假定第一个分页就是完整列表。
- 控制并发、查询时间范围及响应数据量，遇到限流按照上游要求退避。
- 浏览器自动更新展示数据，服务端缓存减少重复请求；不承诺所有边缘节点的请求能全局合并为一次。

### 7.2 数据含义

- 对齐正常、故障、重试中、维护、暂停、未知等状态，上游不支持的状态不强行映射。
- 数据获取状态与监控运行状态分别记录。上游 API 请求失败不能直接视为监控故障。
- 保留数据时间，API 可附带新鲜度和脱敏诊断；浏览器失败时保留旧数据与更新时间，不重复显示过期提示。首次请求可展示部分成功结果。
- 缺失延迟、历史或证书信息时标记缺失，不填零，不伪造正常状态。
- 历史数据完全使用上游实际保留的内容，保留覆盖范围与统计口径。
- 不直接平均不同来源的可用率，也不以最近 100 条心跳替代全天或长期统计。
- 数据能力差异要能由统一接口表达，页面不能假定两个来源都支持所有指标。

## 8. 缓存与降级

### 8.1 默认节点缓存

- 不配置 KV 也能运行。
- 缓存范围是边缘节点，不是全站唯一缓存。
- 为数据新鲜期与旧数据可用期分别建立明确规则；缓存中仍保留成功结果时，更新失败可以返回旧结果及诊断；浏览器保留旧时间并通过 Toast 显示错误。
- 节点缓存可能被清理；没有可用旧结果或首次获取即失败时，明确返回暂无数据或更新失败。
- 不依赖函数进程内存长期保存数据。

### 8.2 可选 KV

- KV 仅额外保存短期的最近成功快照，不逐条累积心跳或形成长期历史库。
- 启用后提高上游故障时返回旧结果的机会，但不作为强一致的全局锁或瞬时失效机制。
- KV 不可用时降级到节点缓存和正常取数，不使整个站点停止运行。

### 8.3 缓存与公开名单

- 缓存按来源、大分组、监控、查询参数及配置版本隔离，避免不同配置复用错误数据。
- 新部署修改公开范围后，新接口不能从旧配置缓存中返回已移除的监控。
- Peekaping 动态状态页名单的有效期与刷新规则需要一并设计。不能因为详细数据缓存仍在，就跳过名单检查；无法确认有效公开范围时不扩大可访问集合。
- 缓存有效期、旧数据最大保留期、刷新频率和请求预算在详细实现设计中统一制定，本文不将早期举例的秒数当作已确认值。

## 9. 接口边界

- 本站只提供页面需要的只读接口，不提供上游监控的创建、修改、删除等管理功能。
- 浏览器只能指定本站允许的分组、监控及受限查询参数，不能自行传入上游 URL、凭证、任意路径或请求方法。
- 详情请求必须检查当前公开范围，不能只凭一个已知监控 ID 查询上游。
- 服务端只返回允许公开的字段，不直接透传上游完整监控配置、请求头、目标地址或原始错误信息。
- API Key 不发送到浏览器，不能将其作为公开只读凭证。
- 不将 CORS 或前端隐藏条目视为权限控制，公开范围在服务端执行。

## 10. 后续设计范围与验证依据

本阶段确定需求与基础架构。下一阶段设计 UI/UX，包括页面内容、交互、手机布局、加载与错误反馈、状态呈现及图表。随后形成完整页面规格与实施计划，选择具体依赖版本、接口响应结构、来源能力映射、配置字段和缓存参数。

后续实现至少验证以下行为，本文不声称这些检查已经执行：

- 两类来源分别完成分页、筛选和按需取数，超出首个分页的监控不遗漏。
- 两级切换、默认首组、「全部」去重和排序符合配置。
- 同一监控跨子分组的展示设置一致，不同大分组的 ID 不冲突。
- 不在公开名单的监控、恶意参数和任意上游地址不能通过本站查询。
- 新配置不能复用旧配置的公开数据；动态状态页名单不会被详情缓存绕过。
- 无 KV、启用 KV、KV 故障、节点缓存丢失、首次失败和部分失败均能降级。
- 状态与取数错误分离，缺失数据和不同统计口径不被伪造或混算。
- 简中与英文匹配、英文回退、浏览器时区、UTC 回退、手动设置持久化和恢复自动均正确。
- 构建产物不包含实际密钥或完整服务端配置。
- 在 EdgeOne 预览部署验证函数、缓存、可选 KV、前端深层路由及运行限制；本地通过不能替代平台验证。
